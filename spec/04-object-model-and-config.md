# 04. Object model and configuration: ruvm-qom and ruvm-qapi

This document specifies the two L1 crates that every other part of ruvm is configured through. ruvm-qom is the object model: types, classes, interfaces, properties, links, the composition tree and lifecycle hooks. ruvm-qapi parses QEMU's `qapi/*.json` schema at build time, generates Rust types, QMP dispatch and visitors, and produces introspection output identical to QEMU's `query-qmp-schema`. The compatibility rule for both is strict: every QOM type name, property name, property type string, QOM path, QAPI name and error string that a management tool can observe is QEMU's, byte for byte. The internal representation is ours. Document 03 covers the lock domains that device state lives in, document 18 covers QMP and HMP as a management surface, and document 20 shows how a new crate registers types.

## What has to match QEMU

Management software talks to QOM through five channels, and each one pins down part of the design.

| Channel | What it exposes | Consequence for ruvm-qom |
|---|---|---|
| `qom-list`, `qom-get`, `qom-set`, `qom-list-get` | Paths, property names, property type strings such as `child<pl011>` and `link<pci-bus>`, values | Composition tree and property tables must be reproducible exactly, including anonymous names like `device[3]` |
| `qom-list-types`, `qom-list-properties`, `device-list-properties` | Type names, parent chain, abstract flag, class properties with descriptions and default values | Type registry must keep QEMU names and inheritance, and class properties must be enumerable without an instance |
| `-object`, `object-add`, `object-del` | User creatable types and their QAPI-described properties | Object creation from `ObjectOptions` (qapi/qom.json), `complete()` semantics of `user-creatable` |
| `-device`, `device_add`, `-global`, `-set` | Device type names, qdev property names and their string parsers | Property parsers must accept exactly the strings QEMU accepts, and reject exactly what it rejects |
| Machine types with versions | `pc-q35-11.1`, `virt-11.1`, compat props | Per-version `GlobalProperty` arrays applied in QEMU's order |

libvirt is the heaviest user. It probes `qom-list-properties` and `device-list-properties` at start-up to build its capability cache, it uses `qom-get` on `/machine/peripheral/<id>` paths, and it addresses devices by the `id` it assigned. Anything that changes names, property type strings, or default values shows up as a capability difference in libvirt's `qemucapabilitiesdata` tests, which document 22 runs against ruvm.

## QOM in QEMU, briefly

QOM (qom/object.c) is a single-inheritance class system with interfaces, written in C. A type is registered with a `TypeInfo` that names the type and its parent and gives `instance_size`, `instance_init`, `instance_post_init`, `instance_finalize`, `abstract`, `class_size`, `class_init`, `class_base_init`, `class_data`, an `is_available` hook and a list of interfaces. Classes are created lazily by copying the parent class and running `class_init`. Objects carry a reference count and a hash table of dynamic properties; class properties live on the class. A property has a name, type string, and getter, setter, release and resolve hooks. Two property kinds are special: `child<T>` properties, which make the object a child in the composition tree and give it a canonical path, and `link<T>` properties, which are references to other objects stored as paths (with flags `OBJ_PROP_LINK_STRONG`, `OBJ_PROP_LINK_DIRECT`, `OBJ_PROP_LINK_CLASS`). The root object has system containers created at start-up; in the reference tree `object_root_initialize()` creates `audiodevs`, `chardevs`, `objects` and `backend`, and the machine lives at `/machine` with its own containers `unattached`, `peripheral` and `peripheral-anon`.

qdev (hw/core/qdev.c) builds on this: `TYPE_DEVICE` adds a `realized` boolean property, static properties declared with `DEFINE_PROP_*` macros, buses, GPIO lines, clocks, a `vmsd` pointer and the resettable interface. Properties declared with `DEFINE_PROP_*` cannot be set after realize unless their `PropertyInfo` has `realized_set_allowed` (see `qdev_prop_allow_set()` in hw/core/qdev-properties.c), and the error text for that case is part of the observable surface: `Attempt to set property '%s' on device '%s' (type '%s') after it was realized`.

## Type registration in Rust

Each Rust type that is a QOM type has a static `TypeInfo` generated by a derive macro and registered into a link-time distributed slice. There is no central list and no `module_init()` constructor function.

```rust
// ruvm-qom/src/registry.rs
#[linkme::distributed_slice]
pub static QOM_TYPES: [&'static TypeInfo] = [..];

pub struct TypeInfo {
    pub name: &'static str,                 // QEMU type name, e.g. "pl011"
    pub parent: Option<&'static str>,       // "sys-bus-device"
    pub abstract_: bool,
    pub interfaces: &'static [&'static str],
    pub class_init: fn(&mut ClassBuilder),  // class properties, vtable overrides
    pub instance_new: Option<fn(&ClassRef) -> ObjRef>,
    pub is_available: Option<fn() -> bool>, // accel or host dependent types
    pub rust_type: fn() -> core::any::TypeId,
    pub module: Option<&'static str>,       // "hw-display-virtio-gpu" when built as a module
}

#[macro_export]
macro_rules! register_type {
    ($info:expr) => {
        #[linkme::distributed_slice($crate::registry::QOM_TYPES)]
        static _REG: &'static $crate::TypeInfo = &$info;
    };
}
```

At start-up, ruvm-system builds the type table from `QOM_TYPES` once: a hash map from name to a `TypeImpl` node that stores the resolved parent pointer, the interface list, and a lazily created class. Duplicate names are a fatal error at start-up with both registration sites printed, which catches the common mistake of two crates claiming the same QEMU type. The table is immutable after start-up except for module loading (document 20), which appends under the control lock before any object of the new types can exist.

Class creation follows `type_initialize()` in qom/object.c: the parent class is initialized first, its class struct is copied, the interface classes are created, `class_base_init` hooks of all ancestors run, then this type's `class_init`. The ordering matters because class properties registered by a parent are visible in the child, and a child's `class_init` may override defaults set by the parent (for example `DeviceClass::user_creatable = false` for board-only devices). ruvm keeps the same ordering so that class property tables are populated in the same sequence as QEMU. The order is observable: libvirt does not depend on it, but QEMU's own tests (`tests/qtest/device-introspect-test.c`) compare help output, and `-device foo,help` output is compared by iotests in a few places.

### Objects, references and casting

An object is a heap allocation containing a common header followed by the Rust struct.

```rust
#[repr(C)]
pub struct ObjectHeader {
    class: ClassRef,                 // &'static-like pointer into the type table
    refcount: AtomicU32,
    parent: AtomicPtr<ObjectHeader>, // composition parent, null for roots
    props: PropTable,                // dynamic (per instance) properties
}

pub struct Obj<T: ?Sized + Object> { ptr: NonNull<ObjCell<T>> }
```

`Obj<T>` is a strong reference with QOM semantics: cloning it is `object_ref()`, dropping it is `object_unref()`, and the finalize sequence on the last unref runs `instance_finalize` of each type from most derived to root, then releases dynamic properties (which unparents children), then frees. `Weak` references are not exposed; QOM does not have them, and link properties without `OBJ_PROP_LINK_STRONG` behave as borrowed pointers whose validity is guaranteed by the composition tree. ruvm models that with `LinkRef<T>`, which holds the target's path and a cached pointer, and is only dereferenced through an accessor that checks the target is still attached (unrealize of a linked-to device clears links pointing at it, as `object_property_del_child()` and the link release callbacks do in QEMU).

Casting is by QEMU type name, not by Rust `TypeId`, because the cast target may be an interface and because QEMU's `object_dynamic_cast()` semantics (walk the parent chain and interface list) are what `-device` and QMP code depend on. Each `TypeInfo` also records the Rust `TypeId` of the concrete struct, so `obj.downcast::<Pl011>()` checks both that the type is `pl011` or a subtype and that the Rust layout is the one expected; a subtype implemented in a different Rust struct (for example `pl011_luminary`, which in QEMU only changes the ID bytes) embeds its parent struct as its first field and the derive macro generates the upcast.

Interfaces are Rust traits. A class stores, for each interface it implements, a pointer to a static vtable for that trait object, keyed by interface type name.

```rust
pub trait Interface: 'static { const TYPE_NAME: &'static str; }

impl ClassRef {
    pub fn interface<I: ?Sized + Interface>(&self) -> Option<&'static I::VTable>;
}

// Resettable is the interface from hw/core/resettable.c
pub trait Resettable: Object {
    fn phases(&self) -> ResettablePhases;           // enter, hold, exit
    fn state(&self) -> &ResettableState;            // count, hold_phase_pending, exit_phase_in_progress
    fn child_foreach(&self, f: &mut dyn FnMut(&dyn Resettable, ResetType));
}
```

`object_class_dynamic_cast()` to an interface name returns the interface class; in ruvm the equivalent returns the vtable. `qom-list-types` with `implements=` walks the same table.

## Properties

A property in ruvm-qom has the same fields as QEMU's `ObjectProperty`: name, type string, description, optional default value, getter, setter, resolve and release. Getters and setters do not use a C visitor; they convert between the Rust field and a `QValue`, the ruvm equivalent of QEMU's `QObject`.

```rust
pub enum QValue {
    Null,
    Bool(bool),
    Int(i64),       // QNum with I64 kind
    Uint(u64),      // QNum with U64 kind, kept distinct for qom-get output
    Double(f64),
    Str(Box<str>),
    List(Vec<QValue>),
    Dict(QDict),    // insertion ordered, as QDict iteration order leaks into JSON output
}

pub struct PropertyDef {
    pub name: &'static str,
    pub type_name: TypeName,             // "uint32", "bool", "str", "link<pci-bus>", "child<pl011>"
    pub description: Option<&'static str>,
    pub default: Option<fn() -> QValue>, // reported as "default-value"
    pub get: Option<Getter>,
    pub set: Option<Setter>,
    pub flags: PropFlags,                // SET_AFTER_REALIZE, LEGACY_STRING, DEPRECATED, ...
}
```

Two input paths reach a setter, and they differ in how scalars look. QMP (`qom-set`, `object-add`, `device_add` in JSON form) delivers typed JSON: `{"value": 5}`. The command line (`-device foo,bar=5`, `-global foo.bar=5`, `-set device.id.bar=5`, `-object` in dotted form) delivers strings. QEMU handles this with different visitors: the QObject input visitor for JSON, and either the keyval variant of it or the legacy string input visitor and the qdev property `set` functions for strings. In ruvm, a setter receives a `PropInput` that is either `Typed(&QValue)` or `Str(&str)`, and the generated setter for each Rust field type implements both with QEMU's parsing rules. The string rules are the ones users trip over, so they are listed in the QemuOpts section below.

Dynamic properties are supported because QEMU uses them heavily, and some of them are observable: every object has the class property `type`, devices add `parent_bus` and `hotpluggable` and `hotplugged`, children appear as `child<...>` entries, CPUs add feature flags at instance init on x86, memory regions attached to a device appear as `child<memory-region>` entries under the device. Per-instance properties are stored in a small vector in the object header (most objects have fewer than 16), searched linearly, falling back to a hash map above 32 entries.

### The derive macro

Static properties, which are what `DEFINE_PROP_*` expresses in C, are declared with attributes on the device struct. The derive generates a `const` table, so class initialization only copies pointers.

```rust
#[derive(Object, Device)]
#[qom(name = "pl011", parent = "sys-bus-device")]
pub struct Pl011 {
    #[parent] parent: SysBusDevice,

    #[property(name = "chardev")]              // PropertyInfo type "str", backend lookup
    chr: CharBackendFrontend,

    #[property(name = "migrate-clk", default = true)]
    migrate_clk: bool,

    regs: DomainCell<Pl011Regs>,               // not a property
    irq: [IrqOut; 6],
    clk: ClockIn,
    iomem: MmioRegion,
    id: &'static [u8; 8],
}
```

The property's QOM type string is derived from the Rust field type through a trait, `impl QomPropType for bool { const NAME: &str = "bool"; }`, `u32` is `"uint32"`, `u64` sizes declared with `#[property(kind = size)]` are `"size"`, `LinkRef<PciBus>` is `"link<PCI>"` or whatever QEMU prints for that link. Cases where QEMU's type string does not follow from the C type (`"on/off/auto"` for `OnOffAuto`, `"str"` for `DEFINE_PROP_CHR` and `DEFINE_PROP_DRIVE`, `"int32"` for some enums) are handled by the per-kind `PropertyInfo` equivalent, `PropKind`, and there is a CI test (`cargo xtask qom-diff`) that starts QEMU and ruvm with the same target and machine, runs `device-list-properties` and `qom-list-properties` for every type both know, and diffs names, type strings, descriptions and default values.

### child<> composition and QOM paths

`object_property_add_child(parent, name, child)` does three things in QEMU: it creates a `child<T>` property on the parent, takes a reference on the child, and sets the child's `parent` pointer, which defines its canonical path. ruvm-qom's `Obj::add_child(&self, name, child)` does the same, with the same failure modes: adding a child that already has a parent is a programming error (QEMU asserts), and a name collision returns the QEMU error `attempt to add duplicate property '%s' to object (type '%s')`.

Array-style names use QEMU's convention: a name ending in `[*]` is replaced by the first free `[N]`. Several paths contain counters that depend on creation order, and ruvm keeps the counters and the order.

| Path | Created by | Counter |
|---|---|---|
| `/machine/unattached/device[N]` | `qdev_realize()` for a device with no parent | Global static incremented at realize time, not at creation |
| `/machine/peripheral/<id>` | `-device ...,id=<id>` and `device_add` with id | None |
| `/machine/peripheral-anon/device[N]` | `-device` or `device_add` without id | Global counter in system/qdev-monitor.c |
| `/objects/<id>` | `-object` and `object-add` | None, id mandatory |
| `/chardevs/<id>`, `/audiodevs/<id>` | `-chardev`, `-audiodev` | None |
| `/machine/unattached/sysbus`, `/machine/q35`, `/machine/peripheral` | Machine init | Board-specific |

The unattached counter is incremented at realize time, which means that a board that creates two devices and realizes them in the opposite order gets swapped numbers. Because libvirt and some tests address onboard devices by these paths (`/machine/unattached/device[0]` is the first CPU on many x86 configurations), each ruvm board is required to realize devices in the same order as its QEMU counterpart, and document 22's `qom-tree` differential test compares the full `qom-list` recursive output of both emulators after start-up for every machine type.

### link<> properties

A link property stores a reference to another object and is set either by path string (`qom-set` with `"/machine/peripheral/foo"`, or a command line property value) or directly by board code. In Rust:

```rust
#[property(name = "memory", link, flags = STRONG)]
memory: LinkRef<MemoryRegion>,

#[property(name = "iommu", link, check = allow_before_realize)]
iommu: LinkRef<dyn IommuMemoryRegion>,
```

The `check` hook mirrors `object_property_allow_set_link` and `qdev_prop_allow_set_link_before_realize()`. When set from a string, the path is resolved as QEMU resolves it: an absolute path, or a partial path that must match exactly one object in the tree (`object_resolve_path_type()` with ambiguity detection). Ambiguous partial paths return QEMU's error. A link declared with `#[sync_peer]` also becomes an edge in the lock domain graph of document 03.

### qom-list, qom-get, qom-set

These commands are thin: path resolution, then the property's getter or setter under the right lock. `qom-get` on a device property takes the device's domain lock for the duration of the getter. `qom-set` on a property whose setter changes topology (a link that rewires an IRQ, a `realized` toggle) takes the control lock first. `qom-list-get` (added in QEMU 10.1) is supported and returns properties in the same order as `qom-list`. The order of `qom-list` results is the property iteration order of `object_property_iter_next()` in qom/object.c: instance properties first, then the class properties of the most derived class, then each parent class up to the root. Both instance and class properties are stored in a `GHashTable`, so within each group the order is GLib hash order. That order is an accident but observable, so ruvm-qom stores properties in insertion order and a small shim (reimplementing `g_str_hash` and GHashTable probing) reorders `qom-list` output to match. The `qom-diff` test covers it; if QEMU ever sorts this output the shim goes away.

## Devices on top of QOM

`#[derive(Device)]` implements `ruvm_hw_core::Device` glue: the `realized` property, static property registration, `vmstate()` returning the static description generated by `#[derive(VmState)]` (document 17), and the resettable interface. The device author writes the logic in an `impl` block:

```rust
pub trait Device: Object + Resettable {
    fn realize(&self, cx: &mut RealizeCtx) -> Result<()>;
    fn unrealize(&self, cx: &mut RealizeCtx) {}
    fn reset(&self, ty: ResetType, phase: ResetPhase) {}
    fn vmstate(&self) -> &'static VmStateDescription;
}
```

The `realized` property setter implements `device_set_realized()` from hw/core/qdev.c: check the bus, run `realize`, then realize child buses, register with the reset tree, register vmstate with the instance id, and on failure unwind in reverse order. After `realize` succeeds, properties without `SET_AFTER_REALIZE` reject writes with QEMU's message.

## User creatable objects and -object

Types that implement the `user-creatable` interface (`TYPE_USER_CREATABLE` in include/qom/object_interfaces.h) can be created with `-object` and `object-add`. Since QEMU 6.0 the accepted input is described by the QAPI union `ObjectOptions` in qapi/qom.json, discriminated by `qom-type`, with one branch per creatable type (`memory-backend-file`, `iothread`, `secret`, `rng-random`, `throttle-group`, `tls-creds-x509`, and so on). `object-add` is declared `'boxed': true` with `ObjectOptions` as its data, which means the QMP command and `-object` share one validated input format.

ruvm follows the same path. `-object` accepts either keyval syntax or JSON (a leading `{`), converts it to a `QDict`, deserializes it into the generated `ObjectOptions` enum (so an unknown property or a wrong type is rejected with the same QAPI error QEMU gives, before any object exists), then creates the object: `object_new(qom-type)`, set each property, run `UserCreatable::complete()` (the `complete` callback that QEMU calls through `user_creatable_complete()`), and add the object as `/objects/<id>`. `object-del` runs `can_be_deleted()` and fails with QEMU's error if the object is in use (a memory backend mapped by a DIMM, an iothread with attached devices).

Early versus late creation is inherited from `object_create_early()` in system/vl.c. Some types must exist before the machine is created or before the accelerator is configured (secrets used by other options, memory backends named by `-machine memory-backend=`, `-object` types needed by chardevs), and others must be created after the accelerator (anything that probes accelerator capabilities). ruvm reproduces the decision function verbatim as a match on the type name, because the same `-object` order that works in QEMU must work in ruvm, and because the phase at which an object is created changes whether a property error is reported before or after other errors.

```rust
pub trait UserCreatable: Object {
    fn complete(&self) -> Result<()> { Ok(()) }
    fn can_be_deleted(&self) -> bool { true }
}

#[derive(Object, UserCreatable)]
#[qom(name = "iothread", parent = "event-loop-base", interfaces = ["user-creatable"])]
pub struct IoThreadObject {
    #[parent] base: EventLoopBase,        // aio-max-batch, thread-pool-min/max
    #[property(name = "poll-max-ns", kind = int64)] poll_max_ns: AtomicI64,
    #[property(name = "poll-grow", kind = int64)]   poll_grow: AtomicI64,
    #[property(name = "poll-shrink", kind = int64)] poll_shrink: AtomicI64,
    #[property(name = "poll-weight", kind = int64)] poll_weight: AtomicI64,
    reactor: OnceLock<ReactorHandle>,
}
```

## -device: JSON and legacy syntax

QEMU accepts `-device` in two forms. If the argument starts with `{` it is parsed as JSON into a `QDict` and later passed to `qmp_device_add()`; otherwise it is parsed as QemuOpts into the `device` option group, where the first unnamed value is the implied `driver` key. `device_add` is declared in qapi/qdev.json with `'gen': false`, because its arguments are the device's properties and cannot be described statically, and it carries the features `json-cli` and `json-cli-hotplug` that let libvirt detect JSON support. The legacy form is created first: `qemu_create_cli_devices()` iterates the QemuOpts `device` list, then the JSON list, so mixing the forms reorders devices relative to the command line. ruvm does the same.

The practical difference between the forms is typing. With JSON, `"bootindex": 1` is an integer and `"bootindex": "1"` is rejected by the integer property's setter, exactly as for QMP. With QemuOpts every value is a string, and the qdev property setters parse it: sizes accept `K`, `M`, `G`, `T` suffixes, booleans accept `on`, `yes`, `true`, `y`, `off`, `no`, `false`, `n` (see `qapi_bool_parse()` in qapi/qapi-util.c), enums accept their QAPI names, and link properties accept paths or ids. ruvm's `PropInput::Str` path runs the same parsers, including the ones with odd grammars (`DEFINE_PROP_PCI_DEVFN` accepts `slot.fn` or a raw number, `DEFINE_PROP_MACADDR` accepts colon-separated hex, `DEFINE_PROP_RESERVED_REGION` accepts `start:end:type`).

The flow for both forms in ruvm is:

```
-device string or JSON / device_add arguments
   -> QDict (strings for legacy, typed for JSON)
   -> pop "driver", "bus", "id"; validate id with id_wellformed()
   -> look up type; check DeviceClass::user_creatable, hotpluggable if after machine ready
   -> choose bus: explicit "bus" path, or first free bus of the right type (qdev_find_default_bus rules)
   -> object_new; apply compat props, then -global (device_post_init order)
   -> set remaining properties in QDict order
   -> add as child of /machine/peripheral/<id> or /machine/peripheral-anon/device[N]
   -> realize (with hotplug handler pre_plug/plug if hotplugging)
```

Leftover keys that are not properties produce QEMU's `Property '<driver>.<name>' not found`. ruvm keeps the order in which properties are set equal to QDict iteration order, which for a JSON `-device` is the order of keys in the JSON text and for QemuOpts is the order of options. That matters for the rare devices whose setters depend on each other (for example `virtio-blk-pci` with both `vectors` and `num-queues`, where the defaulting logic runs at realize and not in the setter, but a few older devices do validate in setters).

## QemuOpts and its quirks

QemuOpts (util/qemu-option.c) is the legacy option parser behind `-device`, `-drive`, `-netdev` (partly), `-chardev`, `-machine`, `-smp`, `-numa`, `-fw_cfg` and others. It is older than QAPI, and many of its rules are accidents that users now depend on. ruvm implements it as a separate module, `ruvm_qapi::opts`, and does not try to express it through keyval, because the two disagree on several inputs.

1. Escaping. A literal comma inside a value is written as `,,`. There is no other escape. `file=a,,b.img` is the file `a,b.img`.
2. Implied first key. Option lists with `implied_opt_name` (`device` uses `driver`, `netdev` uses `type`, `drive` has none) treat a leading value without `=` as that key: `-device e1000,id=n0`.
3. Short-form booleans. In lists that permit it, a bare `foo` means `foo=on` and `nofoo` means `foo=off`. QEMU prints the deprecation warning `short-form boolean option '<name>' deprecated` followed by `Please use <name>=on instead`, with a special case suggesting `nodelay=` for `delay`. ruvm prints the same lines.
4. `help` and `?`. A bare `help` or `?` in the option string is a help request (`-device e1000,help`), unless the list disallows it.
5. The `id` key is special: it is stored outside the option dictionary, must satisfy `id_wellformed()` (a letter followed by letters, digits, `-`, `.` and `_`), and duplicates are rejected with `Duplicate ID '<id>' for <group>`.
6. Merging. Lists with `merge_lists` set (`-machine`, `-smp`, `-rtc`, `-boot`, `-accel` in some paths) merge repeated options into one set, with later keys overriding earlier ones. Lists without it create one entry per occurrence.
7. Repeated keys in one option. For most lists the last occurrence wins; for a few consumers (`-numa`, some `-drive` suboptions) all occurrences are visited in order. ruvm's `Opts` keeps every occurrence in order and lets the consumer choose, as QEMU's `QemuOpts` does with its `QTAILQ`.
8. `-set group.id.key=value` modifies an already parsed option set by id, and `-global driver.prop=value` (or `-global driver=d,property=p,value=v`) registers a global property. Both are applied at the same points as in QEMU: `-set` right after parsing, `-global` in `device_post_init`.

A single differential test corpus, taken from QEMU's own `tests/unit/test-qemu-opts.c` and `tests/unit/test-keyval.c` plus the command lines in the libvirt test suite's `qemuxmlconfdata` directory, is run through both parsers and the resulting QDicts are compared.

The newer keyval syntax (util/keyval.c) is used by `-blockdev`, `-object`, `-audiodev`, `-display`, `-compat`, and (in keyval mode) `-netdev`. Its grammar is `key=value` pairs separated by commas, keys may be dotted paths (`server.host=...`) that build nested objects, numeric key fragments build arrays with no gaps allowed, `,,` escapes a comma, key fragments are 1 to 127 characters, and every scalar is a string. The keyval parser produces a `QDict` whose leaves are strings; the keyval flavor of the QObject input visitor then converts strings to the schema type during deserialization. `ruvm_qapi::keyval` implements this grammar, and the conversion lives in the deserializer (next section).

## Compat properties and machine versions

Versioned machine types exist so that a guest started with `-machine pc-q35-11.0` sees the same hardware after the host upgrades to a newer QEMU. The mechanism is a list of `GlobalProperty` entries (driver, property, value, plus `used` and `optional` flags, from include/qom/compat-properties.h) attached to the machine class. Each release adds a `hw_compat_X_Y[]` array in hw/core/machine.c (generic) and per-architecture arrays such as `pc_compat_X_Y[]` in hw/i386/pc.c. A version's machine options function calls the next newer version's function and then appends its arrays with `compat_props_add()`, so `pc-q35-11.0` includes the arrays for 11.0 plus everything newer versions need to override. The entries in the current development tree's `hw_compat_11_1` array, for example, turn off the `x-migrate-fetch-addr-64bit` property of `sysbus-ehci-usb` and `pci-ehci-usb` for older machine types.

Application order is defined in qom/compat-properties.c and hw/core/qdev.c: `object_apply_compat_props()` applies three slots in order (accelerator compat props, machine compat props, then sugar properties registered by legacy command line options through `object_register_sugar_prop()`), and `device_post_init()` then applies user `-global` properties, so the user wins. A compat entry whose driver matches a type or any of its parents applies to all subtypes. Entries marked `optional` are skipped silently if the property does not exist; others are fatal errors for sugar properties and assertion failures for machine and accelerator ones.

ruvm stores compat arrays as static slices next to the board, generated from a declarative table so that a new release is a one-line change:

```rust
// ruvm-hw-core/src/compat.rs
pub struct GlobalProperty {
    pub driver: &'static str,
    pub property: &'static str,
    pub value: &'static str,
    pub optional: bool,
}

pub static HW_COMPAT_11_0: &[GlobalProperty] = &[ /* copied from hw/core/machine.c */ ];
pub static HW_COMPAT_10_2: &[GlobalProperty] = &[ /* ... */ ];

// ruvm-machine-x86/src/q35.rs
ruvm_machine::versioned_machine! {
    family = "pc-q35", latest = (11, 1), alias = "q35",
    versions = [
        (11, 1) => [],
        (11, 0) => [HW_COMPAT_11_0, PC_COMPAT_11_0],
        (10, 2) => [HW_COMPAT_10_2, PC_COMPAT_10_2],
        // older versions listed down to the oldest QEMU 11.1 still ships
    ],
    options = |v, mc| { if v < (10, 1) { mc.set_default_something(false); } },
}
```

The macro generates one `TypeInfo` per version (`pc-q35-11.1-machine`, following QEMU's `<name>-machine` type naming), sets `alias = "q35"` and `is_default` on the latest, and builds each version's compat vector by concatenating the arrays of all newer versions in the same order as the nested C calls. Non-property differences between versions (QEMU sets machine class fields in the version options functions, such as `smbios_legacy_mode` or default NIC choices) go into the `options` closure. The `used` flag is kept at runtime, as in QEMU, so that `-global` entries that matched nothing produce the same warning.

Compat arrays are copied from QEMU, not re-derived. `cargo xtask compat-sync` parses hw/core/machine.c and the per-arch board files from a QEMU tag with a small C-initializer parser and regenerates the Rust tables; CI fails if the committed tables differ from the output for the reference tag. Machine versions that QEMU has removed (QEMU 11.0 removed old i440FX and Q35 versions, per the canon) are not provided either, since migration from those versions is not possible with QEMU 11.1 as the reference.

## QAPI in ruvm

### The schema is QEMU's schema

ruvm vendors QEMU's `qapi/*.json` files (46 files in the reference tree, rooted at qapi/qapi-schema.json) unmodified into `ruvm-qapi/schema/`, pinned to the reference tag. ruvm does not add commands to that namespace. ruvm-specific commands, if any are ever needed, use the `x-ruvm-` prefix in a separate schema file whose entities are marked `unstable`, and are compiled out of the default build so that `query-qmp-schema` stays identical. Updating to a new QEMU release is a vendored-file update plus regeneration, and the diff of generated code is the review artifact.

The current QEMU schema has no target conditionals, which simplifies the multi-call binary. In the reference tree every `'if'` in the schema is a host or build configuration symbol (`CONFIG_VNC`, `CONFIG_SPICE`, `CONFIG_LINUX`, `CONFIG_BLKIO`, `CONFIG_POSIX`, `HAVE_HOST_BLOCK_DEVICE` and so on), and target-specific commands such as `query-sev` in qapi/misc-i386.json and `query-gic-capabilities` in qapi/misc-arm.json are present in every system emulator binary. So every system emulator built from one configuration has the same schema, and one ruvm binary serves one introspection table for all argv[0] personalities. Target-specific commands called on the wrong target return the same errors QEMU returns (usually `GenericError` with a "not supported" message from the stub).

Build conditions are mapped to cargo features. `CONFIG_VNC` is the `ui-vnc` feature of ruvm-cli, `CONFIG_BLKIO` is `block-blkio`, `CONFIG_LINUX` is `cfg(target_os = "linux")`. The mapping lives in one table in ruvm-qapi's build script; an unmapped symbol is a build error, so a QEMU update that introduces a new condition cannot be silently treated as true or false. When comparing introspection output with QEMU (document 22), the QEMU side is built with the configure flags that correspond to the ruvm feature set under test.

### Parser and generator

The build script of ruvm-qapi runs `ruvm-qapi-gen`, a Rust port of QEMU's scripts/qapi (parser.py, expr.py, schema.py, and the generators types.py, visit.py, commands.py, events.py, introspect.py, features.py). We port it because a cargo build should not need Python and the generator must emit Rust. The port keeps the Python code's structure (same class names, same passes, same error messages for malformed schemas) so that later changes to scripts/qapi can be ported by diffing. A CI job runs QEMU's `tests/qapi-schema/*.json` negative and positive test cases through both implementations and compares the error text and the pretty-printed schema. The generator handles the full language, including `pragma` exception lists, unions with `discriminator`, `alternate`, all command flags (`boxed`, `gen`, `success-response`, `allow-oob`, `allow-preconfig`, `coroutine`), conditions with `all`, `any` and `not`, and the `deprecated` and `unstable` features.

### Generated Rust types

Every QAPI entity becomes a Rust item. The mapping is fixed so that code written against it reads predictably:

| QAPI | Rust |
|---|---|
| `enum` | `#[repr(u32)] enum` with a `const NAMES: &[&str]` table; wire names are the QAPI names |
| `struct` | `struct` with `pub` fields; optional members (`*name`) are `Option<T>` |
| `struct` with `base` | base members inlined as fields, plus a generated `as_base()` view type, because QAPI flattens bases on the wire |
| `union` | a struct holding the base members and an `enum` for the variant data, keyed by the discriminator enum |
| `alternate` | an `enum` with one variant per branch, chosen by the JSON type of the input |
| `any` | `QValue` |
| `null` | `()` |
| built-ins `int`, `int8` to `uint64`, `size`, `number`, `bool`, `str` | `i64`, `i8` to `u64`, `u64`, `f64`, `bool`, `String` |
| array `['T']` | `Vec<T>` |

Member names are converted with the same rules QEMU uses for C names (dashes to underscores, Rust keywords get a trailing underscore instead of QEMU's `q_` prefix, since the prefix is only a C convention and never appears on the wire). Structures used on hot paths do not exist, since QAPI is a control-plane interface; the generated code optimizes for exact error behavior, not speed.

As an example, for the schema fragment

```
{ 'struct': 'ObjectPropertyInfo',
  'data': { 'name': 'str', 'type': 'str', '*description': 'str', '*default-value': 'any' } }
```

the generator emits:

```rust
#[derive(Clone, Debug, PartialEq)]
pub struct ObjectPropertyInfo {
    pub name: String,
    pub r#type: String,
    pub description: Option<String>,
    pub default_value: Option<QValue>,
}

impl QapiType for ObjectPropertyInfo {
    const NAME: &'static str = "ObjectPropertyInfo";
    fn visit_in(v: &mut dyn InputVisitor, name: Option<&str>) -> Result<Self> { /* generated */ }
    fn visit_out(&self, v: &mut dyn OutputVisitor, name: Option<&str>) { /* generated */ }
}
```

### Visitors: serde or not

The obvious design is serde derives on the generated types plus custom keyval and opts deserializers. We use serde only at the edges and generate our own visitor code for the QAPI types, and the reason is error messages. QEMU's QObject input visitor produces errors like `Invalid parameter type for 'size', expected: integer`, `Parameter 'driver' is missing` and `Parameter 'foo' is unexpected` in a precise order that depends on the order of visiting (members in schema order, then a check for leftover keys), and it builds the parameter name from the full dotted path (`server.host`). serde's derived `Deserialize` visits in input order, reports unknown fields as found, and formats paths differently; matching QEMU would need a hand-written `Deserialize` per type, which is what the generator emits anyway.

So the generated `visit_in` code follows QEMU's generated `visit_type_*` functions structurally: start a struct, visit each member in schema order (optional members are visited only if present), visit variant members after reading the discriminator, check for unvisited keys, end the struct. The input visitors are:

1. `QObjectInput` for QMP and JSON command line arguments, strict about JSON types. It mirrors qapi/qobject-input-visitor.c.
2. `KeyvalInput` for keyval command line options, which accepts strings for every scalar and parses them to the requested type (`"on"` for bool, decimal or hex for integers, size suffixes for `size`), and which rejects typed input it did not expect. It mirrors `qobject_input_visitor_new_keyval()`, including the special case that an empty string for an optional struct member means an empty struct in some paths.
3. `StringInput` for the legacy string visitor used by `qom-set` on some properties and by `-numa` and `-smp` style integer lists (`"1-3,5"`). It mirrors qapi/string-input-visitor.c, range expansion and its limit on list size included.
4. `OptsInput` for options still parsed by QemuOpts and then visited, as QEMU's qapi/opts-visitor.c does for `-netdev` in legacy form and `-numa`.

Output goes through `QObjectOutput`, which builds a `QValue`, and `ruvm_qapi::json` serializes a `QValue` to text with QEMU's exact formatting from qobject/json-writer.c: in compact mode a comma is followed by a space and every member name by `": "`, doubles are printed with `%.17g` in the C locale (so `0.1` comes out as `0.10000000000000001`), and non-ASCII characters are escaped the way `quoted_str()` escapes them. That formatting is observable to any client that compares raw text, and some test harnesses do.

serde is still used where the formats are ours: `ruvm run` configuration files (TOML) and internal tooling. A `serde::Serialize` impl is generated for every QAPI type by delegating to the output visitor, so tools can use serde_json with QAPI types when exact QEMU formatting does not matter.

### Commands and events

Each command becomes a trait method on a per-module handler trait, and a dispatch table is generated with the command's flags.

```rust
pub struct QmpCommandDef {
    pub name: &'static str,                    // "qom-get"
    pub handler: fn(&mut QmpCtx, QDict) -> Result<QValue>,
    pub allow_oob: bool,
    pub allow_preconfig: bool,
    pub coroutine: bool,                       // runs as a task on the main reactor
    pub success_response: bool,
    pub features: FeatureSet,                  // deprecated, unstable
}
```

The marshaling function visits the arguments into the generated argument struct, calls the handler, and visits the return value out. Commands with `'gen': false` (`device_add`, `netdev_add` in its legacy form, `qom-get` style commands that take `any`) get a hand-written marshaler. Commands marked `'coroutine': true` in QEMU (in the reference schema exactly two: `block_resize` and `screendump`) run as async tasks on the main reactor so they can wait on IO without blocking the monitor, which is the same behavior as QEMU's coroutine dispatch in qapi/qmp-dispatch.c.

The `-compat` option (qapi/compat.json) controls how deprecated and unstable members and commands behave: `deprecated-input=accept|reject|crash`, `deprecated-output=accept|hide`, `unstable-input=accept|reject|crash`, `unstable-output=accept|hide`. The generated visitors carry each member's feature set and consult the policy, as QEMU's generated code does through `compat_policy_input_ok()`.

Events are generated as functions that build the event's data and hand it to the monitor layer with a timestamp. Rate limiting of events (`RTC_CHANGE`, `BALLOON_CHANGE`, `QUORUM_REPORT_BAD`, `VSERPORT_CHANGE` and the others in `monitor_qapi_event_conf` in monitor/monitor.c) is applied in ruvm-monitor with QEMU's per-event periods.

### Introspection

`query-qmp-schema` returns a list of `SchemaInfo` objects describing every command, event, type, and built-in, generated by scripts/qapi/introspect.py. Two details make byte-identical output nontrivial. First, introspection masks the names of non-builtin types: `_name()` in introspect.py replaces each type name with a decimal string in order of first use during the generator's traversal, unless the generator was run with `--unmask-non-abi-names`. So the numbers depend on the order in which the visitor reaches types, which depends on the order of entities in the schema and on the traversal rules for commands, events and their argument types. Second, conditions: entities whose `'if'` is false are omitted from the reply. The numbering does not move when they are, because the generator assigns numbers before the C preprocessor removes anything, so a type keeps its number in every configuration and the numbers in a reply simply have gaps. Checking against a Homebrew QEMU 11.1 build confirmed this.

ruvm's generator reproduces introspect.py's traversal exactly (same `visit_needed` filter, same deferred emission of used types in `visit_end()`, same mapping of all integer types to `int` in `_use_type()`, same implicit `q_empty` branches for enum values a union does not list) and evaluates conditions against the cargo feature set at build time, after numbering. The output is a static byte string of the JSON reply, computed at build time, so `query-qmp-schema` costs a memcpy. The CI check runs QEMU's `scripts/qapi-gen.py` on the same vendored schema with the matching configuration, extracts the introspection literal from the generated qapi-introspect.c, and compares it with ruvm's static bytes.

Putting the pieces together for one option shows where each module sits.

## Sample device: PL011 UART

The PL011 is a good sample because QEMU has both a C model (hw/char/pl011.c) and an experimental Rust model (rust/hw/char/pl011/src/device.rs), so the comparison is concrete. The QEMU Rust model keeps its registers in a `BqlRefCell<PL011Registers>`, a cell that checks at runtime that the BQL is held; ruvm's version keeps them in a `DomainCell`, and the dispatcher, not the device, takes the lock.

The observable surface this code must match: QOM type `pl011` with parent `sys-bus-device`, subtype `pl011_luminary` that only changes the ID bytes; properties `chardev` (string, chardev id) and `migrate-clk` (bool, default true); one 4 KiB MMIO region named `pl011`; six output IRQ lines (the combined interrupt plus five individual ones, `qemu_irq irq[6]` in include/hw/char/pl011.h); a clock input named `clk`; VMState section `pl011` version 2, minimum version 2, with the field order of `vmstate_pl011` (a 4-byte unused field, then `flags`, `lcr`, `rsr`, `cr`, `dmacr`, `int_enabled`, `int_level`, the 16-entry `read_fifo`, `ilpr`, `ibrd`, `fbrd`, `ifl`, `read_pos`, `read_count`, `read_trigger`), and a subsection `pl011/clock` that is sent only when `migrate-clk` is on.

```rust
// crates/ruvm-hw-char/src/pl011.rs
use ruvm_hw_core::prelude::*;

const FIFO_DEPTH: usize = 16;
static ID_ARM: [u8; 8] = [0x11, 0x10, 0x14, 0x00, 0x0d, 0xf0, 0x05, 0xb1];
static ID_LUMINARY: [u8; 8] = [0x11, 0x00, 0x18, 0x01, 0x0d, 0xf0, 0x05, 0xb1];

#[derive(Default, VmState)]
#[vmstate(name = "pl011", version = 2, minimum_version = 2,
          post_load = Self::post_load, subsections = [PL011_CLOCK])]
pub struct Pl011Regs {
    #[vmstate(unused = 4)] _pad: (),
    flags: u32,
    lcr: u32,
    rsr: u32,
    cr: u32,
    dmacr: u32,
    int_enabled: u32,
    int_level: u32,
    read_fifo: [u32; FIFO_DEPTH],
    ilpr: u32,
    ibrd: u32,
    fbrd: u32,
    ifl: u32,
    read_pos: i32,
    read_count: i32,
    read_trigger: i32,
}

#[derive(Object, Device)]
#[qom(name = "pl011", parent = "sys-bus-device")]
pub struct Pl011 {
    #[parent] parent: SysBusDevice,
    #[property(name = "chardev")] chr: CharFrontend,
    #[property(name = "migrate-clk", default = true)] migrate_clk: bool,
    regs: DomainCell<Pl011Regs>,
    #[mmio(name = "pl011", size = 0x1000, ops = Self)] iomem: MmioRegion,
    #[sysbus_irqs] irq: [IrqOut; 6],
    #[clock_in(name = "clk", on_update = Self::clock_update)] clk: ClockIn,
    #[instance_init(Self::ID_DEFAULT)] id: &'static [u8; 8],
}

impl Pl011 { const ID_DEFAULT: &'static [u8; 8] = &ID_ARM; }

impl MmioOps for Pl011 {
    fn read(&self, cx: &AccessCtx, offset: u64, _size: AccessSize) -> MemResult<u64> {
        let mut r = cx.state(&self.regs);
        let v = match offset >> 2 {
            0x00 => { let v = r.pop_fifo(); self.update(&r); self.chr.accept_input(); v }
            0x01 => r.rsr as u64,
            0x06 => r.flags as u64,
            0x08 => r.ilpr as u64,
            0x09 => r.ibrd as u64,
            0x0a => r.fbrd as u64,
            0x0b => r.lcr as u64,
            0x0c => r.cr as u64,
            0x0d => r.ifl as u64,
            0x0e => r.int_enabled as u64,
            0x0f => r.int_level as u64,
            0x10 => (r.int_level & r.int_enabled) as u64,
            0x12 => r.dmacr as u64,
            0x3f8..=0x3ff => self.id[((offset - 0xfe0) >> 2) as usize] as u64,
            _ => { guest_error!("pl011_read: Bad offset 0x{:x}", offset); 0 }
        };
        Ok(v)
    }

    fn write(&self, cx: &AccessCtx, offset: u64, _size: AccessSize, value: u64) -> MemResult<()> {
        let mut r = cx.state(&self.regs);
        match offset >> 2 {
            0x00 => { self.chr.write_all_blocking(&[value as u8]); r.int_level |= INT_TX; }
            0x11 => r.int_level &= !(value as u32),         // ICR
            0x0e => r.int_enabled = value as u32,           // IMSC
            0x0b => { r.lcr_write(value as u32); }          // LCR_H, resets FIFO on FEN change
            // remaining registers as in hw/char/pl011.c
            _ => guest_error!("pl011_write: Bad offset 0x{:x}", offset),
        }
        self.update(&r);
        Ok(())
    }

    fn valid() -> AccessConstraints { AccessConstraints::any_size(1, 4) }
}

impl Pl011 {
    fn update(&self, r: &Pl011Regs) {
        let flags = r.int_level & r.int_enabled;
        self.irq[0].set(flags != 0);
        for (i, mask) in IRQ_MASKS.iter().enumerate() {
            self.irq[i + 1].set(flags & mask != 0);
        }
    }
}

impl Device for Pl011 {
    fn realize(&self, cx: &mut RealizeCtx) -> Result<()> {
        self.chr.set_handlers(cx, Self::can_receive, Self::receive, Self::event)?;
        Ok(())
    }
    fn reset(&self, _ty: ResetType, phase: ResetPhase) {
        if phase == ResetPhase::Hold { self.regs.with(|r| r.reset()); }
    }
    fn vmstate(&self) -> &'static VmStateDescription { Pl011Regs::VMSTATE }
}

register_type!(Pl011::TYPE_INFO);

#[derive(Object, Device)]
#[qom(name = "pl011_luminary", parent = "pl011")]
pub struct Pl011Luminary { #[parent] parent: Pl011 }
impl Pl011Luminary { #[instance_init] fn init(&mut self) { self.parent.id = &ID_LUMINARY; } }
register_type!(Pl011Luminary::TYPE_INFO);
```

Reviewers should check these points in every device. Guest errors are logged, never returned as `Err`; `MemResult` errors are for bus-level failures such as a decode error on an unimplemented region. The chardev write is blocking because the C model blocks the vCPU on the chardev write (`qemu_chr_fe_write_all`), and changing that would change guest-visible timing under flow control; the chardev backend (document 15) makes the blocking write cheap for the common case of a socket or stdio. `can_receive` and `receive` run on the main reactor under the same domain lock, which gives G4 from document 03. The `reset` hold phase writes registers, and because reset runs with vCPUs paused, no MMIO can interleave with it.

A second sample, a device with a timer, is worked through end to end in document 20 (the PL031 RTC), including tests.

## Decisions made in this document

1. The QAPI generator is a Rust port of scripts/qapi, validated against QEMU's `tests/qapi-schema` cases, rather than a Python dependency at build time.
2. QAPI conditions are mapped to cargo features through one explicit table; unmapped conditions fail the build. Since the reference schema has no target conditionals, one introspection table serves all argv[0] personalities of a build.
3. Generated QAPI types use generated visitor code that mirrors QEMU's visitors for error text and ordering; serde impls are provided as a convenience layer only.
4. `qom-list` output order is made to match GLib hash iteration order through a compatibility shim, tested by `cargo xtask qom-diff`.
5. Compat property tables are generated from QEMU sources by `cargo xtask compat-sync` and checked in CI; ruvm never hand-edits them.
6. ruvm-specific QMP commands use the downstream prefix `__io.github.tamnd.ruvm_`, carry the `unstable` feature, and are absent unless extensions are enabled (the `ruvm` personality or `RUVM_EXTENSIONS=1`), so that `query-qmp-schema` matches QEMU in the `qemu-*` personalities (documents 02 and 25).
7. `-object` early and late classification is a verbatim port of `object_create_early()`.
