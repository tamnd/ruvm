# 08. ruvm-jit: host backends and runtime

This document covers everything between ruvm IR (document 07) and a running vCPU: the host backends and their instruction selection, register allocation for both tiers, code buffer management and W^X, the TB cache and jump cache, block chaining, indirect branches, the softmmu TLB, self-modifying code, MTTCG, atomics, exit and interrupt checks, the TCG plugin ABI, icount and record/replay hooks, profiler integration, and the plan to reach 2x QEMU 11.1 TCG. QEMU source references are to the 11.1 tree, where the backends live in tcg/<host>/tcg-target.c.inc and the runtime in accel/tcg. Note that in 11.1 the backend directories are aarch64, loongarch64, ppc64, riscv64, s390x, sparc64, x86_64, and tci; 32-bit hosts are gone, and the `CPUTLBEntry` comparators are `uintptr_t` because only 64-bit hosts remain.

## The HostBackend trait

```rust
pub trait HostBackend: Send + Sync + 'static {
    const NAME: &'static str;
    type Reg: Copy + Eq + Into<u8>;
    fn caps(&self) -> &HostCaps;                        // detected ISA features, vector widths, atomics
    fn reg_info(&self) -> &RegInfo<Self::Reg>;          // allocatable set, callee-saved, reserved (env, tmp), ABI
    fn constraints(&self, op: Opcode, ty: Type) -> Option<&'static OpConstraint>; // None = not supported, expand
    fn emit_prologue(&self, e: &mut Emitter);           // shared once per code region, like tcg_target_qemu_prologue
    fn emit_op(&self, e: &mut Emitter, op: &LoweredOp<Self::Reg>);
    fn emit_tlb_fast_path(&self, e: &mut Emitter, m: &MemAccess<Self::Reg>) -> SlowPathLabel;
    fn emit_slow_paths(&self, e: &mut Emitter, pending: &[SlowPath<Self::Reg>]);
    fn patch_jump(&self, site_rx: usize, site_rw: *mut u8, target: usize); // tb_target_set_jmp_target
    fn flush_icache(&self, rx: usize, rw: *mut u8, len: usize);
}
```

`OpConstraint` is the Rust form of TCG's constraint sets (tcg-target-con-set.h and tcg-target-con-str.h): per operand a register class, an optional alias to an output (two-address ops on x86), and which immediate forms the instruction can encode (`'i'`, x86's sign-extended 32-bit `'e'`, Arm's logical immediate `'L'`, and so on). Ops the backend does not implement are expanded by the generic lowering layer before register allocation, the equivalent of TCG's `TCG_TARGET_HAS_*` fallbacks, except that in ruvm the decision is made at lowering time instead of at frontend emission time (document 07 explains why).

### Interpreter

TCI in QEMU interprets TCG ops encoded in a bytecode after the regular register allocator runs, so the interpreter sees physical "registers" (an array) and immediates. It is slow (every op is a switch dispatch) but portable. ruvm-jit-interp uses the same idea with two improvements. It uses threaded dispatch: since Rust's `become` is not stable, handlers are generated by a macro into a `match` that LLVM turns into a jump table, with a `#[cfg]` option for a copy-and-patch stencil build when clang is available at build time. And it fuses the common pairs `ld_env` plus op, and `brcond` after `setcond`, into superinstructions. The interpreter implements the full softmmu fast path in Rust, so its TLB behavior is identical to native backends. It is the reference implementation in differential testing: any mismatch between the interpreter and a native backend on the same IR is a backend bug.

## Instruction selection

Tier 1 does instruction selection as a single forward pass fused with register allocation and emission, as TCG does in `tcg_gen_code`. There is no separate selection DAG. The patterns that matter are small and are handled at lowering:

1. Immediate folding by constraint: an operand whose value is a constant and whose constraint allows the immediate form is encoded directly. x86 `add r64, imm32`, Arm `add x, x, #imm12{, lsl 12}`, logical immediates on Arm (bitmask immediates) and RISC-V `andi`.
2. Address mode folding for `ld_env`/`st_env`: `env` plus a constant offset is always a single instruction on every first-class host (x86 disp32, Arm scaled imm12 or unscaled imm9, RISC-V imm12 with a fallback through a temporary for large offsets; `env` is biased so the hot part of CPU state is within the short range, as QEMU does with `CPUNegativeOffsetState` placed just before `env`).
3. Compare and branch fusion: `setcond` whose only use is `brcond` becomes a compare and a conditional branch; `TSTEQ` and `TSTNE` become `test`/`tst`.
4. Extension folding: `extu_i32_i64` of a result produced by a 32-bit op is free on x86-64 and aarch64 (32-bit ops zero the upper half) and becomes `add.uw` style or `zext.w` on RISC-V with Zba.
5. Host flags: when the IR carries a host-flags hint (document 07), the flag-setting form of the arithmetic instruction is selected and the following `flags_use` becomes a conditional branch or conditional select without recomputation. The hint is dropped if any op between the definition and the use clobbers host flags, which the backend knows per op.
6. Rotate and deposit patterns: `deposit` with constant position and length maps to `bfi`/`bfxil` on Arm, to `mov` of a sub-register on x86 when the position and length match 8 or 16 bits at offset 0 or 8, and otherwise to shift and mask.

Tier 2 runs a slightly richer selector over the region: it matches multi-op trees for addressing (base plus scaled index plus displacement on x86, `ldr x, [base, index, lsl #n]` on Arm), `madd`/`msub`, conditional select chains, and it uses the same emitter functions as tier 1.

## Register allocation

### Tier 1: local allocation

Tier 1's allocator is a port of the algorithm in tcg/tcg.c (`tcg_reg_alloc_op`, `tcg_reg_alloc_mov`, `tcg_reg_alloc_call`, `temp_sync`, `temp_save`), because it is fast, well tested, and generates acceptable code for single blocks. It is a forward pass over the op list: for each op, satisfy input constraints (load from memory or move between registers, allocating from the constraint's class and preferring the register hinted by liveness), free inputs that die, allocate outputs (honoring output-input aliasing), then apply the sync and discard decisions liveness made for globals. Spilling picks a register holding a value with a memory copy first, then any register, and writes the value to its slot in `env` (for slots) or a frame slot in the TB's stack area (for temporaries). Calls spill all caller-saved registers holding live values.

Two changes from TCG. First, liveness computes a "preferred register" hint for each value from its next use (for example the host's argument register for a value that is next passed to a helper, or the output register of a two-address op), which TCG does in part with `output_pref`; ruvm applies it consistently to inputs as well, which removes most register-to-register moves around helper calls. Second, slots that are read more than twice in a block and are not clobbered by calls are pinned to callee-saved registers at the block entry, so a guest loop counter read in every iteration does not bounce through `env`.

Complexity is O(n times r) worst case where r is the number of host registers scanned on allocation, effectively linear.

### Tier 2: linear scan over regions

Tier 2 uses linear scan on SSA, following Wimmer and Franz ("Linear Scan Register Allocation on SSA Form", CGO 2010), with lifetime holes and interval splitting as in Wimmer and Mössenböck ("Optimized Interval Splitting in a Linear Scan Register Allocator", VEE 2005). Why linear scan and not graph coloring or a backtracking allocator like LLVM's greedy or Cranelift's regalloc2: regions are up to 4,096 guest instructions and compile on a background thread with a latency target of a few milliseconds per region, and linear scan on SSA needs no interference graph. Poletto and Sarkar's original linear scan (TOPLAS 1999) showed code within a small margin of graph coloring at a fraction of the compile time; the SSA variant removes the need for a separate liveness fixpoint because SSA liveness can be computed in one pass over blocks in a suitable order.

The steps: order blocks in reverse postorder with loop bodies contiguous; number instructions with gaps of two; build intervals with holes from SSA liveness; process intervals by start position, assigning the free register with the furthest next-use position or splitting at the optimal position before the conflict; spill at the lowest loop depth between definition and use; resolve at block edges with parallel moves; and destruct phis into those moves. Guest slots promoted to SSA get a spill location equal to their `env` slot, so a spill of a guest register costs nothing extra at region exit, because the value must be written to `env` then anyway. The EuroSys 2026 LCCRA paper (Meng et al.) makes the same observation for LLVM-based DBTs.

Fixed registers: `env` is pinned in a callee-saved register on all hosts (x86-64 `rbp` in TCG, `x19` on aarch64, `s0` on riscv64; we keep TCG's choices so the prologue and exception unwinding match). The softmmu fast path needs two or three scratch registers; tier 2 models them as short intervals that clobber specific registers at each memory op, so values live across memory ops avoid them.

## Code buffer management and W^X

### Layout

The code buffer is one large virtual reservation, divided into regions handed out to translating threads, as in tcg/region.c. QEMU's defaults are 1 GiB for system mode and 128 MiB for user mode, clamped by the host's direct branch range (`MAX_CODE_GEN_BUFFER_SIZE` is 2 GiB on x86-64, 3 GiB on s390x, unlimited on aarch64 and riscv64 because their `goto_tb` falls back to an indirect jump). ruvm uses the same defaults and honors `-accel tcg,tb-size=N` in MiB. The reservation is split into:

1. Code regions, executable, one active region per translating thread so translation needs no lock on the buffer. Region count follows QEMU's `tcg_n_regions`: regions of at least 2 MiB, up to 8 per vCPU thread and never fewer than one per thread, so a thread that translates heavily can take more regions than its share.
2. A metadata area, not executable, for side tables (document 07), TB headers, and jump target slots (`jmp_target_addr` equivalents). QEMU puts the TB struct and the search data inline with the code; separating them keeps code pages dense in the i-cache and iTLB and means the executable mapping contains nothing but instructions.
3. The shared prologue and epilogue and the out-of-line softmmu helper thunks at the start, so every TB can reach them with a direct branch.

When the buffer fills, ruvm does what QEMU's `tb_flush` does: all vCPUs enter an exclusive section, all TBs are discarded, the TB cache and every jump cache are cleared, and translation restarts. Tier-2 regions are discarded with them. A flush stalls every vCPU and forces retranslation of the working set, which is why the default buffer is large; a generational scheme is listed as an open question (document 25), and until it has a correctness argument as simple as the full flush we keep QEMU's behavior.

### W^X on macOS

Apple silicon forbids pages that are writable and executable at once for the same thread. The mechanism is `mmap` with `MAP_JIT` (which requires the `com.apple.security.cs.allow-jit` entitlement under the hardened runtime) and `pthread_jit_write_protect_np(bool)`, which flips the calling thread's view of all MAP_JIT pages between writable and executable. QEMU does the same (`qemu_thread_jit_write` and `qemu_thread_jit_execute` in include/qemu/osdep.h, `MAP_JIT` in tcg/region.c). ruvm does the same with one discipline enforced by type: a `JitWriteGuard` RAII object switches to write mode on creation and back to execute mode on drop, and every write to the code buffer (translation, `patch_jump` for chaining, unchaining during invalidation) requires `&JitWriteGuard`. Because the toggle is per thread, a vCPU thread patching a jump into another thread's TB does not disturb the other thread. The toggle is not free, so the translator batches: one guard covers a whole translation plus the chaining of its first exits.

On macOS/x86-64 and on Apple silicon when the host is configured without the entitlement, ruvm falls back to split mappings via `mach_vm_remap`, the same as QEMU's `alloc_code_gen_buffer_splitwx_vmremap`.

### W^X on Linux and other hosts

Linux does not force W^X, but hardened kernels (SELinux `execmem` denials, PaX MPROTECT) and good hygiene both argue for it. QEMU supports `-accel tcg,split-wx=on`, which maps the same memfd twice, once RW and once RX, and keeps a constant `tcg_splitwx_diff` between them (`alloc_code_gen_buffer_splitwx_memfd`). ruvm makes split mappings the default on Linux (decision here; QEMU's default is off except where required). Cost: every code write goes through the RW alias, and every code pointer handed to hardware goes through the RX alias; the translator's `Emitter` writes to RW and computes branch displacements relative to RX, which is the same bookkeeping QEMU's `tcg_splitwx_to_rx` does. The run-time cost is limited to extra host TLB entries for the second alias, since the aliases share physical pages; document 21 measures it against split-wx off. The memfd is sealed against growth.

Instruction cache coherence is the backend's `flush_icache` (`__builtin___clear_cache` semantics: `dc cvau; ic ivau; dsb ish; isb` on aarch64, a no-op on x86-64, `fence.i` plus the `riscv_flush_icache` syscall for other harts on riscv64, which is slow enough that ruvm batches it per translation and relies on the syscall only when chaining from another thread).

## TB cache

### Keys and structure

A translation block is identified by `(phys_pc, pc, cs_base, flags, cflags)` where `phys_pc` is the guest physical address of the first byte, `pc` is the guest virtual PC (ignored for comparison when `CF_PCREL` is set), `cs_base` and `flags` come from the target's `get_tb_cpu_state`, and `cflags` carries the cluster id, parallel bit, and count limit. That is QEMU's key (`tb_cmp` in accel/tcg/tb-maint.c).

QEMU stores TBs in a QHT (util/qht.c): a resizable hash table with seqlock-protected lock-free lookups, per-bucket spinlocks for writers, buckets of four entries on 64-bit hosts (`QHT_BUCKET_ENTRIES`), overflow chains, and resizes published under RCU. ruvm's `TbHashTable` implements the same design, with resizes published through ruvm-base's epoch RCU. We keep the design because the workload is overwhelmingly reads (most lookups hit the jump cache first, and QHT is only consulted on a miss), and QHT's readers never write shared cache lines, which a sharded lock-based map cannot match.

Hash function: xxhash-style mixing of the key fields as `tb_hash_func` does; the hash is stored in the TB so jump cache misses can reuse it.

### Per-page lists

For invalidation, each guest physical page that holds code has a list of TBs that intersect it, as in QEMU's `PageDesc` (system mode, a radix table indexed by physical page) or its interval tree (user mode, keyed by virtual address). A TB spanning two pages is on both lists. Page lists are protected by per-page locks acquired in address order to avoid deadlock, the `page_collection_lock` protocol of tb-maint.c.

## Jump cache

Each vCPU has a direct-mapped jump cache of 4,096 entries (`TB_JMP_CACHE_BITS` is 12) mapping guest virtual PC to TB, with QEMU's hash (`tb_jmp_cache_hash_func` mixes page bits and in-page bits so that a TLB flush of one page clears a contiguous range). Entries are `(pc, *const Tb)` pairs written with release stores and read with acquire loads, so a vCPU can invalidate another's entry without a lock. When a TB is invalidated, its entry is cleared in every vCPU's cache (`tb_jmp_cache_inval_tb`). On a guest TLB flush of a page the corresponding range is cleared; on a full TLB flush the whole cache is cleared.

## Block chaining and unchaining

Direct jumps between blocks are patched in place. A TB ending in `goto_tb(n); exit_tb(tb | n)` first executes as a jump to the following `exit_tb`, returns to the cpu loop, which finds the next TB and calls `tb_add_jump(prev, n, next)` to patch the jump in `prev` to point directly at `next`'s code. After that the two blocks run back to back without leaving generated code. Each TB keeps a list of incoming jumps (`jmp_list_head` and `jmp_list_next[2]` in QEMU, tagged pointers with the slot number in the low bits) and its two outgoing targets.

Patching must be atomic with respect to other vCPUs executing the same code. On x86-64 the `jmp rel32` displacement is aligned so the 4-byte field is written with one atomic store. On aarch64 the jump is a single `b` instruction when the target is within 128 MiB, and otherwise an `ldr x, literal; br x` pair where only the literal (the `jmp_target_addr` slot) changes; the patch writes one 32-bit instruction atomically and flushes the i-cache line (tb_target_set_jmp_target). riscv64 emits a patchable `jal` followed by a load of `jmp_target_addr` and a `jalr`; the patch writes a `jal` when the target is within the plus or minus 1 MiB range of its 20-bit offset and a `nop` otherwise, so execution falls through to the indirect form. ruvm keeps these sequences.

Unchaining happens when the target is invalidated: every incoming jump is reset to point to its own `exit_tb` path (`tb_reset_jump`), under the destination's `jmp_lock`, and the target is marked `CF_INVALID` so a racing lookup cannot chain to it again.

Chaining is disabled when the TB has `CF_NO_GOTO_TB` (single-step and some icount cases), and in system mode `goto_tb` is used only when the destination is on the same guest page as the TB start (`translator_use_goto_tb`), because a direct chain bypasses the TLB lookup that would notice a mapping change. In user mode QEMU allows cross-page chaining unless gdb may set breakpoints; ruvm keeps both rules for tier 1. Other transfers use `lookup_and_goto_ptr`.

## Indirect branches and return prediction

An indirect branch (a register jump, a return, an exception return that stays in the same mode) cannot be chained because the target is not known at translation time. QEMU handles it with `lookup_and_goto_ptr`: the generated code calls `HELPER(lookup_tb_ptr)` in accel/tcg/cpu-exec.c, which sets `can_do_io`, computes the current (pc, flags, cs_base) through `get_tb_cpu_state`, checks breakpoints, and calls `tb_lookup`, which tries the per-vCPU jump cache and then QHT. On a hit it returns the host code pointer and the generated code jumps to it with `goto_ptr`; on a miss it returns `tcg_code_gen_epilogue`, which returns to `cpu_tb_exec` and the outer loop translates. The frontend emits `exit_tb` instead when `CF_NO_GOTO_PTR` is set.

ruvm keeps this as the general mechanism and makes the hit path cheaper. The helper call is a full ABI call with the caller-saved registers spilled by the tier-1 allocator; the lookup inside it is a hash, one load of the jump cache entry, and a compare of pc plus a reload of flags. We generate an inline probe of the jump cache before the call: the backend computes `tb_jmp_cache_hash_func(pc)` into a scratch register, loads the `{tb, pc}` pair, compares pc and the cached flags word, and jumps directly to the TB's code on a match. The slow path is the existing helper. The flags compare needs the frontend to provide the current flags word cheaply; for targets where `get_tb_cpu_state` is expensive (x86 in system mode derives flags from several fields) the frontend keeps a cached copy in the CPU state that is updated whenever the inputs change, the same technique QEMU uses for `hflags` on x86 and Arm. Frontends that cannot guarantee the cached copy is current set a capability bit and always take the helper.

Returns get extra help. Guest code executes call and return in pairs, and a return almost always goes to the instruction after the matching call. Rosetta 2 translates x86 `call` and `ret` into Arm `bl` and `ret` so the host's return predictor works, and keeps a side stack of (guest return address, host return address) pairs that is checked on return (dougallj's write-up of Rosetta 2). Box64 has a comparable option, `BOX64_DYNAREC_CALLRET`. ruvm adopts a software return address stack (RAS) in the CPU state, per vCPU, of 16 entries (a fixed ring, overflow drops the oldest). A guest call pushes the guest return address and the host address of the continuation TB if it is already translated, or a stub that resolves it on first use. A guest return pops the top entry, compares the popped guest address against the actual return address in the guest register or stack slot, and on a match jumps to the host address; on a mismatch it falls back to the inline jump cache probe and then the helper. The comparison makes the RAS a prediction only: a guest that manipulates its stack (longjmp, coroutines, return-oriented code in tests) gets correct behavior at the cost of a miss.

The RAS entries hold host code pointers, so they are invalidated with the TB they point to. Rather than track every entry, each entry also stores the TB's generation number, and the pop compares it against the generation stored in the TB header; `tb_flush` bumps a global epoch that clears every RAS lazily on its next use. Mapping guest calls onto host `bl`/`ret`, as Rosetta 2 does, would need the host stack kept in step with guest calls and unwound on exceptions, which conflicts with the rule that generated code holds no host frames across TBs; it is left to document 25.

Frontends mark x86 `call`/`ret`, Arm `bl`/`blr`/`ret`, and RISC-V `jal`/`jalr` whose `rd` or `rs1` is `ra` or `t0` (the unprivileged specification's hint rules) as calls or returns; other indirect jumps use only the probe. In tier 2, hot indirect sites keep a small target profile and region formation (document 07) may inline the dominant target behind a compare.

## Softmmu TLB

In system mode the software TLB maps every guest load and store to a host address for RAM or to a slow path for anything else. ruvm keeps QEMU's data layout, which the backends depend on, and changes only how often the fast path runs.

### Layout

Each vCPU has, per MMU index, a `CPUTLBDescFast` of `{mask, table}` that lives at a negative offset from `env` so the backend can address it with a small displacement, and a `CPUTLBDesc` with the slow-path state. The table holds `CPUTLBEntry` values; on 64-bit hosts each entry is 32 bytes (`CPU_TLB_ENTRY_BITS` is 5), a union of `addr_read`, `addr_write`, `addr_code` and `addend`, each a `uintptr_t`. The comparator fields hold the page-aligned guest virtual address with flag bits in the low bits: `TLB_INVALID_MASK` (bit 6), `TLB_NOTDIRTY` (bit 7) and `TLB_FORCE_SLOW` (bit 8) sit in the part of the comparator that the fast path checks, so any of them forces a mismatch and a trip to the slow path (include/exec/tlb-flags.h). The slow path then consults the full entry (`CPUTLBEntryFull`) for the flags that do not fit, such as `TLB_MMIO`, `TLB_WATCHPOINT`, `TLB_BSWAP`, `TLB_DISCARD_WRITE` and `TLB_CHECK_ALIGNED`. `addend` is the value added to the guest virtual address to get the host address for RAM-backed pages. The fast table's `mask` is `(n_entries - 1) << CPU_TLB_ENTRY_BITS`, so the index computation is a shift and an and that yields a byte offset directly.

ruvm keeps this layout bit for bit in ruvm-jit-core because every backend's fast path hard-codes it.

### Fast path per host

The following sequences are what QEMU 11.1 emits in `prepare_host_addr` for a load with no alignment requirement stronger than the access size; ruvm's backends emit the same shape. Cycle figures are our estimates for a TLB hit with all loads hitting L1, derived from the dependency chain (three dependent loads: mask and table, then the comparator, with the addend load in parallel), and will be replaced by measurements from document 21.

| Host | Sequence (hit path) | Instructions | Estimated latency on hit |
| --- | --- | --- | --- |
| x86-64 | `mov` addr to scratch, `shr` by page bits minus entry bits, `and` with `[env+mask]`, `add` `[env+table]`, `lea` or `mov` of addr plus alignment offset, `and` with page mask, `cmp` with `[entry+cmp_ofs]`, `jne` slow, `mov` addend, access through `[addr+addend]` | about 10 | 3 dependent L1 loads, roughly 12 to 15 cycles before the access |
| aarch64 | `ldp` mask and table, `and` with `lsr` shifted operand, `add`, `ldr` comparator, `ldr` addend, optional `add` for alignment, `and` with page mask, `cmp`, `b.ne` slow, register-indexed access | about 9 | same chain, roughly 10 to 14 cycles |
| riscv64 | `ld` mask, `ld` table, `srli`, `and`, `add`, optional `addi`, `andi` or `li` plus `and`, `ld` comparator, `ld` addend, `bne` slow, `add`, access | 11 to 12 | same chain, core-dependent; no estimate until measured |

The slow path is out of line at the end of the TB (`tcg_out_qemu_ld_slow_path` and friends), reached by the conditional branch, and returns to the instruction after the access. The fast path clobbers two or three scratch registers, which tier 1 models as fixed temporaries and tier 2 models as clobbers of the memory instruction (document 07 and the register allocation section above).

Three things reduce the fast path's share of run time in ruvm. First, tier 2 hoists the index and table computation for accesses that are provably on the same guest page within a region (same base register, offsets within a page, no intervening store that could change the TLB, no helper call that could flush it), and reuses the addend; the comparator check still happens once per page per region entry. Second, tier 2 can merge the check for adjacent accesses to the same page, which is common in stack spills and structure copies. Third, where the guest access is known to be aligned, the alignment masking instruction is dropped. None of these change the layout.

### Victim TLB

A miss in the direct-mapped fast table first checks the victim TLB, 8 entries per MMU index (`CPU_VTLB_SIZE`), searched linearly by `victim_tlb_hit` in accel/tcg/cputlb.c. On a hit the fast entry and the victim entry are swapped, together with their full entries, under the TLB spinlock, and the access retries the fast path. When a fast entry is evicted by a fill, it moves into the victim table in round-robin order. ruvm keeps this unchanged.

### Dynamic resizing

The fast table size per MMU index is dynamic, between `1 << CPU_TLB_DYN_MIN_BITS` (64) and `1 << CPU_TLB_DYN_MAX_BITS` entries, starting at `1 << CPU_TLB_DYN_DEFAULT_BITS` (256). The resize decision is made at flush time by `tlb_mmu_resize_locked`: the descriptor records the maximum number of entries in use during a window of 100 ms. If use exceeded 70% of the table at flush time, the table doubles; if use was below 30% and the window has expired, the table shrinks to the power of two that fits the observed maximum, doubled again if the result would otherwise be above 70% use. Allocation failure retries at smaller sizes. ruvm ports this policy and its constants unchanged: a large table costs flush time for guests that flush often, and a small one costs misses.

### Large pages

The TLB holds one entry per target page even when the guest maps a larger page. `tlb_add_large_page` records, per MMU index, a single `large_page_addr` and `large_page_mask` that covers every large page inserted since the last full flush. A single-page flush that falls inside that range flushes the whole MMU index, since the TLB cannot tell which target pages came from the large mapping. This is conservative and cheap in the common case. ruvm keeps it for tier 1. The obvious improvement, keeping a small set of large-page ranges rather than one covering range, helps guests that mix huge pages and frequent single-page flushes (Linux with transparent huge pages); it is a tier-2 era change gated on a benchmark in document 21.

### IOTLB and MMIO

The full entry (`CPUTLBEntryFull`) holds the physical address, the `MemoryRegionSection` index, the attributes (`MemTxAttrs`) and the slow flags. For pages backed by MMIO, the fill sets `TLB_MMIO` in the comparator, so every access takes the slow path, which dispatches to the device through the memory API (document 05) with the section and the attributes. For RAM pages that contain translated code, the fill sets `TLB_NOTDIRTY` on the write comparator, which is the hook for self-modifying code below. ROM devices and write-discarding regions use `TLB_DISCARD_WRITE`. The slow path also handles unaligned accesses that cross a page by splitting them into two accesses, each with its own lookup, and it handles watchpoints.

The slow path runs Rust code in ruvm-jit, but its behavior must match cputlb.c exactly, including the order of checks (alignment fault before TLB fill on targets that require it, watchpoint before MMIO), since guests observe fault priorities.

### Cross-vCPU flushes

A guest TLB invalidation that must reach other vCPUs, such as an Arm broadcast `tlbi` with the inner-shareable qualifier, uses the `_all_cpus_synced` variants such as `tlb_flush_page_by_mmuidx_all_cpus_synced`. QEMU queues the flush on every other vCPU with `async_run_on_cpu` and queues the source vCPU's own flush with `async_safe_run_on_cpu`, which runs it in an exclusive section after every other vCPU has stopped, so the source does not continue until the flush has happened everywhere. x86 shootdowns need no such variant, because the guest sends IPIs and each vCPU flushes locally. ruvm keeps these semantics and names. The flush work itself is per vCPU and needs no lock beyond the TLB spinlock that protects the full entries against concurrent fills from the owning thread and resizes.

## Self-modifying code

Canon fixes the approach: page protection plus write tracking, not per-store checks in generated code. The two modes do it differently, as QEMU does.

In system mode, guest RAM pages that contain translated code have their `DIRTY_MEMORY_CODE` bit clear in the dirty bitmap (document 05). When the TLB fills a write entry for such a page it sets `TLB_NOTDIRTY` in `addr_write`, so every store to the page misses the fast path. The slow path calls `notdirty_write` (accel/tcg/cputlb.c), which calls `tb_invalidate_phys_range_fast` for the written bytes, marks the page dirty for the other clients, and, once no translated code remains on the page, clears `TLB_NOTDIRTY` in the TLBs so later stores are fast again (`tlb_set_dirty`). Translating code on a page does the reverse through `tlb_protect_code`, which clears the page's code dirty bit; clearing a dirty bit also marks the existing write entries for that page in every vCPU's TLB with `TLB_NOTDIRTY` (`tlb_reset_dirty`). The per-page TB lists described above are what make the invalidation proportional to the code on the page rather than to the cache.

In user mode there is no software TLB for guest stores, so the host MMU does the tracking: when a TB is created from a writable guest page, the page is made read-only with `mprotect` (`tb_lock_page0` and its helpers in accel/tcg/user-exec.c), and the resulting `SIGSEGV` is handled by `page_unprotect` in accel/tcg/user-exec.c, which invalidates the TBs on the page, restores write permission, and restarts the store. Host pages larger than guest pages (16 KiB pages on Apple silicon, 64 KiB on some aarch64 and ppc64 Linux configurations) mean one host page may hold several guest pages; the protection covers the whole host page and the invalidation covers every guest page in it.

The hard case is a store that modifies the TB that is currently executing, or a later instruction of it. Targets whose architecture requires such stores to take effect for the next instruction (x86 and s390x, which set `precise_smc` in their `TCGCPUOps`) need the store to end the TB: `tb_invalidate_phys_page_unwind` detects that the current TB was invalidated, restores the guest state to the storing instruction through the side tables (document 07), and sets `cflags_next_tb` so the next TB is a single instruction and the translation after it sees the new code. Arm and RISC-V require an explicit instruction barrier (`isb`, `fence.i`) before modified code is guaranteed to execute, so their frontends end the TB at the barrier and do not need the unwind. ruvm ports this logic unchanged; QEMU's tests/tcg cases for it are reused by document 21.

Tier 2 regions register on every page their blocks came from, so the same invalidation reaches them. A region invalidated this way is not rebuilt immediately: its blocks drop back to tier 1 and their counters restart, which avoids repeated tier-2 compiles for code that JIT compilers inside the guest keep rewriting.

## MTTCG and exclusive sections

Canon makes MTTCG always on: one host thread per vCPU, running generated code concurrently. QEMU 11.1 enables MTTCG by default only when the target sets `mttcg_supported` and icount is off (accel/tcg/tcg-all.c), and it refuses `thread=multi` with icount. ruvm requires every frontend it ships to be MTTCG-safe; that means frontends emit the memory order the guest architecture requires (document 07), use the atomic IR operations for guest atomics, and never rely on a single-threaded round-robin scheduler for correctness.

Operations that cannot be done concurrently use exclusive sections. `start_exclusive` and `end_exclusive` (cpu-common.c) stop every other vCPU at a safe point (between TBs, through the exit request mechanism below), run the work, and restart them. Their users are TB cache flushes, some TLB flush variants (`async_safe_run_on_cpu`), and the atomic fallback: when an atomic operation cannot be done with host atomics, the generated code calls `HELPER(exit_atomic)`, which raises `cpu_loop_exit_atomic`, and the outer loop runs `cpu_exec_step_atomic`. That function takes the exclusive lock, translates the faulting instruction with `CF_PARALLEL` cleared and `CF_NO_GOTO_TB | CF_NO_GOTO_PTR | CF_NOIRQ | CF_STEP_ATOMIC | 1`, runs that one instruction with every other vCPU stopped, and releases the lock. With `CF_PARALLEL` clear the frontend is allowed to implement the atomic with plain loads and stores. ruvm keeps this mechanism because it is the only simple correct answer for operations the host cannot do atomically, and makes it rare by covering 128-bit operations natively on all first-class hosts.

icount and record/replay are the exception to concurrency. QEMU runs them with the single-threaded round-robin loop (accel/tcg/tcg-accel-ops-rr.c) because the instruction counter and the replay log define a global order. ruvm does not keep a second execution loop for this. New decision: in icount and replay modes each vCPU still has its own thread, but a serial token passes between them in a fixed round-robin order at the same points where QEMU's loop switches vCPUs (after a time slice or an exit), so exactly one vCPU runs generated code at a time and the order is deterministic. Generated code is the same as in single-threaded QEMU for these modes: `CF_PARALLEL` is clear, so atomics compile to plain operations. Document 14 specifies the replay side.

## Atomics

The IR's atomic operations (document 07) carry size, ordering, and the `MO_ATOM_*` atomicity requirement of the guest access. The backends lower them as follows.

| Operation | x86-64 host | aarch64 host | riscv64 host |
| --- | --- | --- | --- |
| Load and store up to 64 bits | plain `mov` (aligned accesses are single-copy atomic) | plain `ldr`/`str`, or `ldar`/`stlr` when the mapping asks for acquire or release | plain `ld`/`sd` with `fence` as mapped |
| Read-modify-write up to 64 bits | `lock` prefixed instruction or `lock cmpxchg` loop | LSE (`ldadd`, `swp`, `cas` families, with `al` variants) when present, otherwise `ldxr`/`stxr` loop | A extension `amo*` and `lr`/`sc` loop, with `.aqrl` as mapped |
| 128-bit compare and swap | `lock cmpxchg16b` (requires the CX16 CPUID bit, probed at start) | `casp`/`caspal` with LSE, otherwise `ldxp`/`stxp` loop | `amocas.q` with Zacas, otherwise `exit_atomic` |
| 128-bit plain load or store | `vmovdqa` when the CPU documents 16-byte atomicity for aligned vector accesses (probed), otherwise `cmpxchg16b` | `ldp`/`stp` with LSE2 for aligned accesses, otherwise `ldxp`/`stxp` | `exit_atomic` unless Zacas makes a CAS-based load acceptable |

QEMU's 128-bit support (the `HAVE_CMPXCHG128` and `HAVE_ATOMIC128_RO` style checks in host/include/*/host/atomic128-*.h.inc) informs this table; ruvm probes the same host features at start in its `HostCaps`. Anything the table cannot do falls back to `exit_atomic` and the serial step described above, which is correct but slow; document 21 includes a counter for how often it happens so that a missed host feature shows up in profiles.

Guest load-linked and store-conditional (Arm `ldxr`/`stxr`, RISC-V `lr`/`sc`, PowerPC `lwarx`/`stwcx.`) are emulated the way QEMU does it: the load records the address and the loaded value in the CPU state (`exclusive_addr` and `exclusive_val` on Arm, `load_res` and `load_val` on RISC-V), and the store-conditional succeeds if a host compare-and-swap of the recorded value to the new value at the recorded address succeeds. This is not exactly the architecture's semantics: an intervening store that writes the same value (the ABA case) does not fail the store-conditional, where real hardware would. Code that uses LL/SC as a compare-and-swap loop cannot tell the difference; code that relies on LL/SC to detect ABA can. An exact reservation, tracked through page protection or a TLB flag, would send every store to a page holding a reservation down the slow path. ruvm keeps QEMU's behavior and lists an exact mode as an open question in document 25.

## Exit requests and interrupt checks

Generated code must stop within bounded time when another thread wants the vCPU: an interrupt is raised, the main loop needs the vCPU to process events, an exclusive section is starting, or the TB cache is being flushed. QEMU does this with one 32-bit load and a compare at the start of every TB. `gen_tb_start` in accel/tcg/translator.c loads `icount_decr.u32` from the negative-offset area before `env` and branches to the exit label if it is negative. The high 16 bits are the exit request: `tcg_kick_vcpu_thread` stores `exit_request` with release semantics and then stores `-1` to `icount_decr.u16.high`, which makes the 32-bit value negative. The low 16 bits are the icount budget when icount is on. `cpu_handle_interrupt` clears the high half with a full barrier (`qatomic_set_mb`) before reading `exit_request` and `interrupt_request`, which pairs with the release store. `CF_NOIRQ` suppresses the check for the one-instruction TBs used for I/O recompilation and atomic stepping.

Because the check is at the start of every TB, a chained loop of TBs still sees a request within one TB. ruvm keeps the check and its placement for tier 1: its cost is one load and one compare-and-branch that the host predicts as not taken, and it doubles as the icount budget check. Tier 2 regions move the check to the region entry and to every loop back edge inside the region, which gives the same latency bound (at most one loop iteration or one straight-line trip through the region) with fewer checks. A region that contains no back edge and fewer instructions than the tier-1 TB limit (512) has only the entry check.

The same exit label also serves `CF_USE_ICOUNT` TBs, where the count is decremented by the TB's instruction count before the compare, and I/O instructions that must be last in a TB for deterministic timing, handled by `cpu_io_recompile` as described in document 07.

## Plugin ABI and instrumentation cost

Canon requires the TCG plugin C ABI to match bit for bit: a plugin built against QEMU 11.1's include/plugins/qemu-plugin.h, which declares `QEMU_PLUGIN_VERSION` 7, loads into ruvm unmodified and sees the same callbacks in the same order. The API implementation lives in ruvm-plugin (document 20) and follows plugins/api.c and plugins/core.c; this section covers the code generation side, which follows accel/tcg/plugin-gen.c.

At translation, the translator calls the plugin translation callbacks after the guest block has been decoded, so the plugin sees each instruction's bytes and can register per-TB and per-instruction work. The registrations are then injected into the IR (`plugin_gen_inject`) at the TB start, before each instruction, and after each memory access. The kinds of work have very different costs, and ruvm keeps each at the cost QEMU pays or lower.

| Registration | Generated code | Relative cost |
| --- | --- | --- |
| `..._exec_inline_per_vcpu` with `QEMU_PLUGIN_INLINE_ADD_U64` or `STORE_U64` | load of a per-vCPU scoreboard entry (base plus `cpu_index` times entry size), add or store, write back | a few instructions, no call |
| `..._exec_cond_cb` with a `QEMU_PLUGIN_COND_*` comparison | inline load and compare of a scoreboard entry, branch around a call | inline cost plus a call when the condition holds |
| `..._exec_cb` | call to the plugin function with `cpu_index` and userdata | full ABI call, which spills caller-saved registers in tier 1 |
| `qemu_plugin_register_vcpu_mem_cb` | store of the callback list pointer into `plugin_mem_cbs` in the CPU state before the access, the normal access, then a call to `qemu_plugin_vcpu_mem_cb` with address, value and `MemOpIdx` | a call per access, plus the hardware address lookup if the plugin asks for it |
| `qemu_plugin_register_vcpu_mem_inline_per_vcpu` | inline scoreboard update after the access | a few instructions per access |

Counting plugins should use inline operations; plugins with per-instruction or per-access calls are dominated by the calls. Document 21 measures the contrib/plugins set on ruvm against QEMU running the same plugins.

Two ruvm rules protect the ABI. Tier 1 block formation follows QEMU's rules whenever a plugin is loaded, so a plugin that counts TBs or looks at TB boundaries sees the same blocks (decided in document 02). And tier 2 is disabled for any TB that carries plugin instrumentation in M9: region formation, register promotion and load forwarding all move or remove the points where callbacks run, and preserving exact callback semantics across them is later work (document 25). Uninstrumented code in the same guest still tiers up.

## icount and record/replay hooks

With `-icount`, each TB is translated with `CF_USE_ICOUNT`: `gen_tb_start` subtracts the TB's instruction count from `icount_decr.u16.low` and exits if the budget would go negative, and I/O instructions follow the rules in document 07 (`translator_io_start`, `can_do_io`, `cpu_io_recompile`). The outer loop refills the budget from `icount_extra` and the virtual clock (`cpu_loop_exec_tb` in accel/tcg/cpu-exec.c and `icount_prepare_for_run` in accel/tcg/tcg-accel-ops-icount.c). ruvm ports these, keeping the exact instruction accounting, since replay logs and `-icount` timing depend on it. Tier 2 is off in icount and replay modes in M9: a region would need to update the budget at every exit and back edge, which is possible but not worth the risk before replay is proven on tier 1.

Record/replay hooks sit outside generated code: interrupts, I/O completions, clock reads and checkpoints go through the replay layer (replay/*.c) at the same points as in QEMU, and the serial token described under MTTCG gives the deterministic vCPU order. Document 14 owns the log format and the hook list.

## perf map and jitdump

QEMU 11.1 supports `-perfmap` and `-jitdump` in both system and user mode (tcg/perf.c). `-perfmap` writes `/tmp/perf-<pid>.map` with one line per TB naming the guest address and, where debug info is available through the guest ELF, the guest symbol. `-jitdump` writes `jit-<pid>.dump` in the Linux perf jitdump format with `JIT_CODE_LOAD` and `JIT_CODE_DEBUG_INFO` records and maps a marker page executable so `perf inject --jit` can find the file. ruvm accepts the same options and writes the same formats, including the prologue record (`perf_report_prologue`). Tier 2 regions are reported as one code load named after the entry block's guest address and symbol with a `tier2` suffix, and their debug info records map host ranges back to each guest instruction using the region's side table (document 07).

## Performance plan

Canon sets the target: 2x the geometric mean of QEMU 11.1 TCG on SPEC CPU2017 intrate, on the first-class guest and host pairs, at M9. Tier 1 alone carries the M4 target in document 21; the rest comes from tier 2. The table below gives where we expect the gain to come from and why. The shares are planning estimates for an x86-64 guest on an aarch64 host, the pair where QEMU loses the most; none are measurements, and document 21 defines how each is measured and reported. They do not add linearly.

| Source | Mechanism | Evidence | Expected share |
| --- | --- | --- | --- |
| Memory model fences | Risotto and Arancini mappings (load then `dmb ishld`, `dmb ishst` then store, `casal` for RMW), adjacent-fence merging, `ldapr` with LRCPC, Apple TSO mode where available (document 07) | Risotto reports fences costing up to 75% (48% on average) and a 6.7% average gain from its mapping alone | large on Arm hosts, none on x86 hosts |
| Register promotion and load/store forwarding | Tier 2 keeps guest registers in host registers across a region instead of loading and storing `env` around every block | the main source of speed in region-based DBTs such as HQEMU (2.4x over QEMU on CINT2006 in its paper) | largest single share |
| Flag liveness | lazy flags in tier 1, dead flag elimination across a region in tier 2 | x86 guests compute flags on most arithmetic, few are read | medium on x86 guests |
| Indirect branches and returns | inline jump cache probe and a return address stack | calls and returns avoid the helper on a hit | medium on call-heavy code (gcc, perlbench, xalancbmk) |
| TLB fast path | per-page check hoisting, merged checks, dropped alignment masks | removes instructions from the most frequent sequence | small to medium |
| Vector and FP | guest vector registers as slots, direct host SIMD mapping, inline host FP under the rules in document 07 | intrate is integer, so this matters more for fprate and real workloads than for the target | small on intrate |
| Translation cost | tier 1 within 1.2x of TCG translation time; tier 2 only on hot code | Instrew measured QEMU spending a large fraction of 602.gcc run time in translation; that time must not grow | protects the gain on short-running benchmarks |

The risks are known ones. Tier 2 compile time can eat the gain on benchmarks with large, flat profiles (gcc), which is why the threshold and region limits in document 07 are tunable and measured. Fence optimization gives nothing on x86 hosts, so the 2x there must come from tier 2 and the branch work alone; document 21 reports each host separately so a good aarch64 result cannot hide a weak x86 one. If the geomean misses 2x at M9, the first candidates are a more aggressive region former and the speculative flag optimization deferred to document 25.

## New decisions in this document

- The host backends are x86-64, aarch64 and riscv64 first class, then ppc64, s390x and loongarch64, plus a threaded interpreter that serves as the differential-testing reference. There is no sparc64 host.
- Split-wx is on by default on Linux. MAP_JIT with a RAII write guard is used on macOS.
- An inline jump cache probe runs before `lookup_tb_ptr`, and each vCPU has a software return address stack of 16 entries validated on pop. Host `bl`/`ret` mapping is deferred to document 25.
- TLB layout, victim TLB and resize policy are kept unchanged; tier 2 hoists and merges checks.
- icount and replay run on per-vCPU threads with a deterministic serial token instead of a separate round-robin loop.
- LL/SC keeps QEMU's compare-and-swap emulation. An exact reservation mode is an open question.
- Tier 2 is disabled for plugin-instrumented TBs and in icount and replay modes at M9.
- Tier 2 regions check for exits at entry and on back edges.
